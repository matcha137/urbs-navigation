# TOKYO発進

**その日の体調と天気で「どこまで行けるか」が変わる人のための、散歩コース提案。**

https://urbs-navigation.chori39.workers.dev/?demo=1

東京都オープンデータカタログサイトの公開データ13件を結合して、
「出発する駅」「散歩に使える時間」「どんな散歩がしたいか」の3つから
立ち寄り先を並べたコースを返す。Cloudflare Workers の1本で動く。

---

## これは何か

「おすすめの観光スポット」は、行ける人にしか役に立たない。
段差があるか、トイレはどのくらい近いか、座れる場所があるか、雨をしのげるか。
これらは公開されているのに、**別々のデータセットに散らばっていて一緒に引けない**。

このアプリは、公園・公衆トイレ・公共施設の3系統を空間結合して、
その日の条件で引ける1つの母集団にした。

そして**足りないものは足りないと画面に書く**。
これがこのプロジェクトで一番強い制約で、以下すべての設計判断がここから来ている。

| 原則 | 具体的にどうなるか |
|---|---|
| データに無い属性は機能にしない | ベンチ数・手すりのデータは存在しない → 手すりは機能から外した |
| 未記入を「非対応」と読まない | バリアフリー列の空欄は `NULL` (不明) のまま。「段差なし」とは表示しない |
| 推定は推定と書く | 座れる場所は面積からの推定。語尾を「〜ありそう」にし、面積の実値を添える |
| 0件になる選択肢は出さない | データが無い区では「屋内で休む」を選べなくし、理由を書く |

### なぜ5区だけなのか

23区すべてのカタログ（2,606データセット）を取り、公園・トイレ・施設の CSV を実際に
ダウンロードして列を数えた。**壁はデータセットの有無ではなく、緯度経度が空欄なこと。**

都市公園一覧は東京都の推奨フォーマットなので、緯度・経度の列は23区すべてに存在する。
しかし値を入れている区は少数だった。墨田・葛飾・練馬・中央・板橋・荒川・千代田・品川は
公園CSVの座標が全行空欄になっている。

住所からのジオコーディングを使えば約1,400公園を足せるが、**推定した座標で
「車椅子対応トイレまで62m」と言うことになる**ため入れていない。
測り方の詳細は [docs/datasets.md](docs/datasets.md) にある。

## 何が分かって、何が分からないか

母集団 **1,411箇所**（公園 991 / 施設 408 / 水辺 11 / 庭園 1）。

| 区 | 箇所 | 段差が分かる | 車椅子対応トイレあり | 屋内 | 区の申告値あり |
|---|---:|---:|---:|---:|---:|
| 江東区 | 409 | 64 | 307 | 120 | 69 |
| 杉並区 | 648 | 0 | 166 | 288 | 0 |
| 新宿区 | 178 | 0 | 0 | 0 | 0 |
| 目黒区 | 126 | 0 | 23 | 0 | 19 |
| 台東区 | 50 | 0 | 29 | 0 | 0 |

この表の 0 は「対応していない」ではなく「**区が値を公開していない**」。
新宿区の場所を開くと段差もトイレも全部「情報なし」と出るが、それが正しい表示になる。

| 画面に出る値 | 出どころ | 実測か推定か |
|---|---|---|
| 車椅子対応トイレまで◯m | 公衆トイレ一覧との空間結合（半径200m以内で最近傍） | **実測**（座標間の直線距離） |
| 段差解消あり | 公共施設一覧の「スロープ、エレベータ、エスカレータ」欄 | **区の申告値**（88件のみ） |
| 屋内 | 施設か公園かの区分 | **実測** |
| 座れる場所が多そう | 公園の面積（5,000/2,000/800㎡で4段階） | **推定**。ベンチのデータは存在しない |
| 水辺 | 場所の名前に川・堀・親水などが残っているか | **推定**。水辺の実データは乗船場11件しかない |
| 天気による距離の短縮 | Open-Meteo の降水確率・気温 | 実測（ただし補正量はこちらの決め） |

### 区によって選べる「散歩のしかた」が違う

`etl/06-station-modes.mjs` が駅ごとに半径1,700m以内の候補数を数え、
3件未満のモードは**フロントで押せなくする**。理由は区の問題か駅の問題かで書き分ける。

| 区 | のんびり | 水辺 | しっかり | 屋内 |
|---|---|---|---|---|
| 江東区（6駅） | ○ | ○ | ○ | ○ |
| 杉並区（6駅） | ○ | 浜田山・永福町のみ | ○ | 荻窪・阿佐ケ谷・高円寺のみ |
| 台東区（4駅） | ○ | — | ○ | — |
| 目黒区（4駅） | ○ | — | ○ | — |
| 新宿区（4駅） | ○ | — | ○ | — |

台東・目黒・新宿に「屋内」が無いのは、施設データが取れないため
（台東は CSV が 404、目黒は 403、新宿はトイレCSVの座標が全行空欄）。

## 動かす

```bash
npm install
```

### ローカル

```bash
npm run dev
```

D1・KV・Vectorize・Workers AI は本番のものに繋がるので `wrangler login` が要る。
管理エンドポイント (`/api/admin/*`) を叩くときだけ `.dev.vars` の `ADMIN_TOKEN` も要る。

### データを作り直す

`data/raw/` の CSV から `db/seed.sql` までを一気に作る。ネットワークには出ない。

```bash
npm run etl
```

内訳は 文字コード統一 → 正規化・名寄せ・空間結合 → 検査 → 駅ごとのモード実測 →
絞り込み → SQL生成。カタログの取得（`npm run etl:catalog`）と CSV のダウンロード
（`node etl/01-probe.mjs`）は調査用で、この流れには入っていない。

### 本番に入れる

```bash
npm run db:schema
npm run db:seed
```

**seed のあとは必ず索引を作り直すこと。** 忘れると自然文検索が古い場所を指す。

```bash
ADMIN_TOKEN=xxxx npm run reindex
```

### 出す・確かめる

```bash
npm run deploy
```

```bash
npm run check
```

`check` は型・フィクスチャ・正規化結果を見る（ネットワーク不要）。
本番に対する通しの確認は `npm run check:api`。
全24駅 × 申告したモードの65通りを叩いて、**押せる組み合わせがすべて候補を返すか**を検査する。
ETL側の判定（JS）と API側の判定（SQL）が二重管理になっているので、ここでズレを捕まえる。

## 構成

ビルドステップは無い。フロントは `public/` の素の ES モジュール1枚。

```
public/          画面。ビルド無し
src/             Worker (Hono)
  routes/        places / suggest / weather / search / admin
  lib/           plan(採点) sql places weather embed intent reason
config/          モード定義・駅・しきい値・プロンプト。ETLとAPIが共有する唯一の正
shared/types.ts  フロントとWorkerが共有する型
etl/             00..06 の連番。mappings/ が区ごとのCSV読み取り
scripts/         検査と索引再構築
db/              schema.sql と生成された seed.sql
docs/            調査・API・デモ台本
```

| バインディング | 使いみち | 落ちたら |
|---|---|---|
| D1 `tokyo_outings` | 1,411箇所（places / place_access / place_source、1.5MB） | 止まる |
| Vectorize `urbs-places` | 自然文検索の索引（1,411件 / 1024次元 / cosine） | ことばの一致に縮退 |
| Workers AI | 埋め込み `bge-m3` / 理由文 `llama-3.3-70b` | 定型文に縮退 |
| KV `CACHE` | 天気30分 / 理由文24時間 | 都度取りに行くだけ |
| Assets `ASSETS` | `public/` の配信 | 止まる |

縮退したことは `degraded` フラグで返し、画面にも書く。黙って質を落とさない。
