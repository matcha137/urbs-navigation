# API

`https://urbs-navigation.chori39.workers.dev`

型は [`shared/types.ts`](../shared/types.ts) が唯一の正。SQL は [`db/queries.sql`](../db/queries.sql) が原本。

疎通と契約の検査:

```bash
node scripts/check-api.mjs
```

## GET /api/health

D1 まで到達できるかを見る。

```json
{ "ok": true, "service": "urbs-navigation", "db": { "ok": true, "places": 1411 }, "ts": "..." }
```

## GET /api/modes

散歩のしかたの選択肢。フロントはラベルをハードコードせずここから引く (T-53)。
`id` / `label` / `hint` / `emoji` を返す。

## GET /api/stations

出発地点として選べる駅。**データを持っている5区の24駅だけ**を返す。
渋谷・池袋・東京などを載せない理由は `config/stations.ts` に実測値付きで書いてある
(最寄りの場所が2km以上先で、30分圏内が0件になる)。

```json
{
  "wards": ["江東区", "杉並区", "台東区", "目黒区", "新宿区"],
  "stations": [
    { "id": "kiyosumi", "ward": "江東区", "name": "清澄白河駅",
      "lat": 35.6816, "lng": 139.7975, "lines": "半蔵門線・大江戸線",
      "modes": ["stroll", "water", "active", "indoor"] }
  ]
}
```

- `wards` は optgroup の並び順。
- **`modes` はその駅で成立する散歩のしかたの実測値。**
  `config/station-modes.json` (`etl/06-station-modes.mjs` が生成) を読んでいる。
  ここに無いモードはフロントで押せなくする。0件の画面を見せないため。

台東区・目黒区・新宿区には屋内施設のデータが無いので `indoor` が入らない。
「水辺を歩く」も名前からの推定なので、当たる場所が3件未満の駅では外れる。

> **二重管理の注意。** `etl/06-station-modes.mjs` のハードフィルタは
> `src/lib/places.ts` の `modeConditions()` を JS で書き直したもの。
> ズレると「選べるのに0件」が起きるため、`scripts/check-api.mjs` が
> **全駅×申告モード (65通り) を本番に投げて**空でないことを検査している。

## GET /api/weather — T-34 / T-35

いまの天気と、それがモードに与える補正。距離は散歩時間にも比例するので `byMinutes` に 30/60/90 を並べて返す。
フロントは `/api/suggest` の `weather` を使うので、これは**補正が効いていることを目で確かめる窓**。

| パラメータ | 例 | 説明 |
|---|---|---|
| `near` | `35.6816,139.7975` | 省略時はデモ起点 (清澄白河駅) |
| `demo` | `true` | 固定の雨。補正の説明に使う |

```json
{
  "weather": { "tempC": 18, "condition": "rain", "summary": "18° · 小雨、14時には上がる", "rainStopsAt": "14:00", "observedAt": "..." },
  "source": "kv",
  "degraded": false,
  "adjust": {
    "good": { "baseMaxDistanceM": 1200, "maxDistanceM": 780, "baseShelterWeight": 0.2, "shelterWeight": 0.6, "note": "雨なので短めに、屋根のある場所を優先しました" }
  }
}
```

`source` は `kv` | `origin` | `demo` | `fallback`。

## POST /api/suggest — T-33

```json
{ "mode": "stroll", "minutes": 30, "lat": 35.6816, "lng": 139.7975, "demo": false }
```

`simulateAiOutage: true` で理由文の生成を飛ばし、ルールベースに落とす (T-73)。
応答の `aiRejected` には検証で落ちた理由が入る（**デバッグ用。画面には出さない**）。

返りは `SuggestResponse` (`plan` + `alternatives` 最大2件 + `weather` + `degraded`)。

## POST /api/search — T-38 / T-39

```json
{ "q": "雨でも濡れない静かなところ", "lat": 35.6816, "lng": 139.7975, "mode": "stroll", "limit": 10 }
```

| フィールド | 説明 |
|---|---|
| `q` | 自然文。200文字まで |
| `lat` / `lng` | 省略可。`mode` と併用すると距離も効く (60分・晴れ基準) |
| `mode` | モードのハードフィルタ (T-32) を検索にも適用 |
| `simulateVectorOutage` | `true` で縮退経路を通す。UI のリハーサル用 (T-39) |

```json
{ "places": [...], "degraded": { "vector": false }, "intent": ["屋内"] }
```

`intent` は問い合わせ文から読み取れた条件のラベル。画面に「屋内で絞りました」と出せる。

`GET /api/search?q=...&mode=...&near=lat,lng` も同じ。手で叩く用。

## POST /api/admin/reindex — T-37

D1 の全件を埋め込んで Vectorize に入れ直す。**ETL で D1 を作り直したら必ず回すこと。**

```bash
ADMIN_TOKEN=xxxx npm run reindex
```

合言葉は Worker のシークレット (`wrangler secret put ADMIN_TOKEN`)。
未設定なら 503 を返す — 開けっ放しにはしない。

## POST /api/admin/forget

指定した id の項目を Vectorize から消す。**D1 から消えた場所の残骸を掃除するためだけのもの。**

索引は id で upsert するので、id の付け方を変えると古い id の項目が誰にも上書きされずに残る。
検索は D1 と突き合わせて落とすので誤答にはならないが、topK の枠を死んだ id が食う。

```bash
curl -XPOST .../api/admin/forget -H 'x-admin-token: …'   -H 'content-type: application/json' -d '{"ids":["park:AA0131083001"]}'
```

**D1 に実在する id は消さない**（`skippedAlive` に数が返る）。
D1 の照会は 90件ずつ、Vectorize の削除は 100件ずつに割っている。どちらも上限があるため。

区を足したとき (T-96) に場所 id を `park:AA…` から `park:koto:AA…` へ変えたので、
江東区由来の 788件が孤児になった。これで掃除した。

`GET /api/admin/index-info` で索引と D1 の件数を突き合わせられる。
`GET /api/admin/inspect/:id` は1件ぶんの埋め込み本文と、保存済みベクトルと
再計算したベクトルの cosine を返す。**索引が古いかどうかはこれで分かる** (1.0 なら最新)。

## 決めごと

### 距離は SQL で出す

D1 は `power()` を許可していない (`SQLITE_ERROR 7500`)。二乗は `x * x` と展開する。
`sin` / `cos` / `sqrt` / `asin` / `radians` は使える。式は
[`src/lib/sql.ts`](../src/lib/sql.ts) の `distanceExpr()` に1箇所だけ置いてある。

内側で `dist_m` を作り外側で `WHERE` をかける二段構え。
SELECT のエイリアスは同じ SELECT の WHERE から参照できないため。

### 三値カラムを潰さない

`step_free` / `slope` は 1 / 0 / NULL の**三値**。NULL は「不明」であって「非対応」ではない。
1,411件のうち 1,347件は段差情報を持たない (公園データに存在しない) ので、

```sql
WHERE step_free = 1                        -- ✗ 公園が全滅する
WHERE (step_free IS NULL OR step_free = 1) -- ○ 「段差ありと明記」だけを外す
```

`scripts/check-api.mjs` はこれを回帰として見張っている
(indoor の結果に `stepFree === null` が1件も残っていなければ失敗する)。

### 行き先にならない施設を除く

公共施設一覧 120件には、**利用者が限定されている施設**が混ざっている。

| 種類 | 件数 | 例 |
|---|---|---|
| 利用者限定の福祉施設 | 10 | あすなろ作業所、深川老人福祉センター、グループホーム新砂 |
| 予約制で普段は入れない | 43 | 三好地区集会所、南砂区民館 |
| そもそも施設ではない | 5 | 道路事務所 |

バリアフリーを売りにするアプリが「あすなろ作業所へ行きましょう」と提案するのは
端的に間違いなので、行き先の母集団から外す (1,411 → 1,099件)。
区が増えて語彙も増えた: 杉並区の「ゆうゆう館」(60歳以上限定)、区営住宅の「アパート」、
閉鎖済みの「旧◯◯会議室」など。区分の列を持たない区は名前で切るしかない。

**D1 からは消していない。** トイレや雨宿りの実在情報としては正しく、
出典カウント (T-92) の根拠でもあるため。行き先クエリでだけ除く。
語彙は [`config/destinations.ts`](../config/destinations.ts) が唯一の正。

> 本来は ETL の除外ルール (`etl/mappings/koto-facilities.mjs` の `EXCLUDE_KEYWORDS`)
> に置くべき性質のもの。移すと再 normalize + 再 seed が要るので、まずは API 側で外してある。

区役所・出張所・防災センターは**落とさず順位だけ下げる** (×0.6)。
ロビーとトイレがあり雨宿りと休憩には実際に使えるため、他に選択肢があるときだけ後ろに回る。

### 天気で候補が消えたら、天気ぶんの短縮を外す

`low` は 250m。雨 (×0.65) で 162m になり、起点によっては候補が 0件になる。
天気による短縮は「好み」だがプロファイルの距離は「約束」なので、
消えたときだけ天気補正を外して引き直し、フッタに「天気ぶんの短縮を外して探しました」と出す。
それでも 0件なら `404 no_candidates` を正直に返す。

### 天気は Open-Meteo → KV 30分キャッシュ

APIキー不要。`current=temperature_2m,weather_code` と `hourly=weather_code` だけを取る。

- **キャッシュキー**は座標を小数2桁 (≈1.1km四方) に丸める。江東区なら数キーで収まる
- **タイムアウト 2.5秒**。デモ中に画面が固まる方が損失が大きい
- **KV への書き込みは `ctx.waitUntil()`** で応答を待たせない
- **KV バインディングが無くても動く** (毎回 origin を叩くだけ)。ローカル開発で効く

WMO コードは4分類 (`clear` / `cloudy` / `rain` / `snow`) に潰す。
**分類を増やさないこと** — `WEATHER_ADJUST` が4つしか持っていない。
雷雨 (95-99) は屋根を優先させたいので `rain` に寄せている。

`rainStopsAt` は hourly を現在時刻から12時間先まで走査して、
最初に雨でも雪でもなくなる時刻。見つからなければ `null` (「今日はずっと雨」)。

### 天気が取れなくても止まらない

天気は**あると嬉しい情報**であって前提ではない。失敗したら
`FALLBACK` (22° / くもり = 補正が 1.0 になる値) + `degraded.weather=true` で続行する。
デモ中に Open-Meteo が落ちてもプランは出る。

本番で確認済み: `/api/weather?near=999,999` は `source:"fallback"`、`degraded:true` を返し、
`adjust` は補正のかからない既定値のままになる。

### 補正の効き方 (T-35)

`effectiveLimits(mode, minutes, weather)` が唯一の入口。距離・ルート上限・歩数・屋根の重みを一括で返す。
距離の予算は `MINUTES` (散歩時間) が持ち、モードは `distanceScale` を掛けるだけ。

| | 距離 | 屋根の重み |
|---|---|---|
| 晴れ / くもり | ×1.0 | 変化なし |
| 雨 | ×0.65 | +0.4 |
| 雪 | ×0.5 | +0.5 |
| 30℃以上 | ×0.6 | — |
| 27℃以上 | ×0.8 | — |
| 8℃以下 | ×0.85 | — |
| 3℃以下 | ×0.65 | — |

気温と天気の補正は**掛け算**。雨で30℃なら ×0.39 まで縮む。

### degraded は嘘をつかないための旗

| フラグ | いまの値 | 外れる時 |
|---|---|---|
| `weather` | 取得できれば `false` | — (T-34 完了) |
| `ai` | 文を1つでも採用できれば `false` | — (T-70〜T-73 完了) |
| `vector` | 索引が使えれば `false` | — (T-36〜T-38 完了) |

UI はこれを見て注記を出す (T-39)。`/api/suggest` の `vector` は
「別の場所を探す導線 (`/api/search`) が使えるか」を伝えるためのもの。
suggest 自体は索引を引かない。

縮退したときの動き:

| 落ちたもの | 代わりに | 見た目 |
|---|---|---|
| Open-Meteo | 22°/くもり (補正 1.0) | 「天気は取得できていません」 |
| Workers AI / Vectorize (検索) | 語彙の層 + 名前の部分一致 | 結果は返る。並びが粗くなる |
| Workers AI (理由文) | ルールベースの文 | 文が事務的になる。内容は正しいまま |

縮退時も語彙の層は効くので、「雨でも濡れない」は屋内だけを返し続ける。

### 自然文検索は「ベクトル + 語彙」の二段

**ベクトルだけでは成立しなかった。**

元データに情景の記述が一切無く、1,411件の説明文が
「◯◯公園。面積 2,975㎡の公園。石島にある。区立公園。車椅子対応トイレが24m以内にある。」
という同じ形をしている。そのため bge-m3 の類似度は **0.34〜0.44 の狭い帯**に固まり、
「雨でも濡れない静かなところ」に屋外の児童遊園が返る。

そこで、問い合わせ文から**データで判定できる条件だけ**を語彙で拾う
([`src/lib/intent.ts`](../src/lib/intent.ts))。

| 語 | 効果 |
|---|---|
| 雨 / 濡れ / 屋内 / 室内 / しのげ | `shelter = 1` のハードフィルタ |
| 車椅子 / バリアフリー / 段差 / トイレ | `accessible_toilet = 1` のハードフィルタ |
| 広い / 大きい / のびのび | 面積 3,000㎡ 以上を上位に |
| 小さ / 近所 / すぐ | 面積 3,000㎡ 未満を上位に |
| 川 / 水辺 / 運河 / 親水 | `riverside` を上位に |
| 公園 / 広場 / 遊園 / 緑地 | `park` を上位に |

**「静か」「景色がいい」は拾わない。** データが無いので拾うと嘘になる。

最終的な並びは `類似度 × 0.65 + 条件一致 × 0.35`。
条件が何も読み取れなければ類似度の順位がそのまま残る。

実測:

| 問い合わせ | 読み取れた条件 | 1位 |
|---|---|---|
| 川沿いを歩きたい | 水辺 | 旧中川・川の駅スロープ |
| 子どもと遊べる広い公園 | 広い・公園 | 江東区立豊洲公園 (24,303㎡) |
| 近所の小さな公園 | 小さい・近い・公園 | 江東区立新木場一丁目第二公園 (114㎡) |
| 本を読める静かな屋内 | 屋内 | 森下文化センター |

「広い」で平均 15,174㎡、「小さい」で平均 485㎡ と、30倍の差が出る。

### 埋め込みの前に定型文を落とす

公共施設一覧の説明欄は、**7つの文化センターが一字一句同じ150字の案内文**を持っている。
そのまま埋め込むと固有の情報 (名前・属性) が共通の定型文に埋もれ、
どの問い合わせにも同じ施設群が返る。

索引を作るとき、全件の説明文を走査して
**25文字以上かつ3箇所以上に出てくる文**を定型文とみなして落としている
(江東区のデータでは7文が該当)。データが変われば定型文も変わるので、
**索引を作り直すたびに計算し直す**。

あわせて、事実から導ける語彙だけを足す — 面積から「広い」「小さい」、
名前から「水辺」。データに無いこと (遊具、景色) は足さない。

### つまずいた上限が3つ

| | 上限 | 症状 |
|---|---|---|
| **D1 バインドパラメータ** | 1文 **100個** | `variable number must be between ?1 and ?100` |
| **Vectorize topK** | **100** | query が例外 → 縮退して `degraded.vector` が立つ |
| **Vectorize 反映** | 約 **2分** | 索引を作り直しても検索結果が変わらない |

D1 の 100個が一番きつい。行き先の除外語19個を**リテラル**にして枠を空け、
`id IN ()` に積むのは `PARAM_LIMIT = 90` までにしてある。
出典の取得 (`fetchSources`) も 90件ずつに割っている。

**デプロイ直後に reindex を走らせないこと。** 反映前の古いコードで索引が作られる。
`GET /api/admin/inspect/:id` の cosine が 1.0 でなければ、索引が古い。

### 理由文は「事実の言い換え」しかさせない

`plan.headline` / `plan.title` / `stops[].note` を Workers AI
(`@cf/meta/llama-3.3-70b-instruct-fp8-fast`) が書く。**数字を含む行
(`summary` / `tags` / `footer`) は生成させない** — 距離や面積を言い換えさせる
理由が無く、間違ったときの実害だけが大きい。

三段構え:

1. **モデルに渡すのは検証済みの事実表だけ。** 元データの自由記述は渡さない
2. **出てきた文を1つずつ検証する** ([`src/lib/reason.ts`](../src/lib/reason.ts) の `validate`)
3. **落ちたフィールドだけ**ルールベースの文に戻す。全滅したら `degraded.ai`

一部だけ AI・一部はルールベース、という状態が普通に起きる。

### 検証で落とすもの (T-72)

| 検査 | 例 |
|---|---|
| データの無い語 | ベンチ / 手すり / 遊具 / 静か / 景色 / 桜 / 営業時間 / 駅から |
| 相手の気分の決めつけ | 気晴らし / 元気を出して / 頑張って / リフレッシュ |
| 事実表に無い数字 | 「トイレが50m以内」(実際は95m) |
| 段差への言及 | `step_free` が不明な場所で「段差なし」 |
| 屋内の主張 | `shelter=0` の公園で「雨をしのげます」 |
| 車椅子対応の主張 | `accessible_toilet=0` の場所で「車椅子対応」 |
| 天気の混入 | 立ち寄り先の理由に「天気は晴れです」 |
| 短すぎる / 長すぎる | 「トイレ」(3字) — ルールベースより情報が減る |

**headline と title はプラン全体の主張**として扱う。1箇所でも段差不明が
混ざれば見出しにも段差のことを書かせない (`planClaimsOf`)。

語を並べる方式は破れる。「段差なし」「段差がない」を禁じたら
**「段差の無さ」で抜けてきた**ので、段差への言及そのものを正規表現で禁じている。
分かっている場所では許すので、言えないことだけが言えなくなる。

`POST /api/admin/validate-probe` で本番と同じ `validate()` を直接叩ける。
`check-api.mjs` はここを 13 件のケースで見張っている。

### 生成文は KV に24時間キャッシュする

キーは `rz:v{PROMPT_VERSION}:{mode}:{事実表のSHA-256}`。

**`config/prompts.ts` を直したら `PROMPT_VERSION` を必ず上げること。**
事実表は変わらないので、版数を混ぜないと古い文が返り続けて
「直したのに変わらない」になる（実際に一度踏んだ）。

### モデルの応答は形が一定しない

llama-3.3 は `response` を**パース済みのオブジェクト**で返してくる。
文字列で返るモデルもあり、`choices[0].message.content` にしか入らないこともある。
`parseJson` は全部受ける。**文字列だと決め打つと `degraded.ai` が黙って立ち続ける。**

### novelty はデータが無い

訪問履歴が無いので「行ったことのなさ」は本来出せない。
候補集合の中でのカテゴリの珍しさで近似しているが、これは弱い指標なので、
1つのプランの中で同じカテゴリを続けて選んだときに ×0.5 する方で実質的に効かせている
(そうしないと `good` が公民館3連発になる)。
