## 23区を全部当たった結果（T-96）

**壁は「緯度経度が空欄」だった。** 公園データは都の推奨フォーマットなので
列は23区すべてに在るのに、値を入れている区は少ない。

「施設のみ」の区（葛飾433件・練馬576件など）も検討したが、
**中身は学校と保育園が半分**で、公園が1件も入っていない。

### 座標が無い区をジオコーディングで足さなかった理由

住所は全区に入っているので、外部のジオコーディングAPIを通せば
墨田・葛飾・練馬などの約1,400公園を足せる。やっていない。

推定した座標で距離を測ると「車椅子対応トイレが62m以内」が推定の上の推定になる。
このアプリは**データが言っていないことを言わない**のが主張なので、
番地レベルの誤差を数十メートル単位の断定に混ぜるのは筋が悪い。

### 「だれでもトイレあり」の読み方が区によって違う

| 区 | 車椅子使用者用トイレ有無 | バリアフリートイレ数 |
|---|---|---|
| 江東区 | 100%充足 (150件) | 数と完全に一致 (150/150) |
| 台東区 | 39%充足 (27件) | 数にしか無い行が5件 |
| 杉並区 | **全行空欄** | 100%充足 (60件) |
| 目黒区 | **全行空欄** | 列名が「多機能トイレ数」(13件) |

そこで **「有」と書かれている、または数が1以上** を「ある」とした。
数の列は空欄ではなく 0 が明記されているので、0 を「無い」と読んでよい。
江東区では両者が完全に一致するため、**この規則で既存の判定は1件も動かない**。
実装は `etl/mappings/_templates.mjs` の `standardToilets`。

`etl/06-station-modes.mjs` が駅ごとに実測して `config/station-modes.json` を作る。
0件になる組み合わせを**選ばせる前に外す**ため。

| 江東区 | ○ 全6駅 | ○ 全6駅 (12〜38件) | ○ | ○ 全6駅 |
| 杉並区 | ○ 全6駅 | △ 浜田山・永福町のみ | ○ | △ 荻窪・阿佐ケ谷・高円寺のみ |

水辺が江東区でしか十分に効かないのは、**名前から水辺を当てているから**。

### 対応（確定・実装済み）

**方針1+2の併用を採用した。**

1. **面積(㎡) を「座れる場所」の代替指標にする** — 面積のある866件すべてに入っている。
   閾値は実分布に合わせて `config/seating-tiers.json` に定義:
   `≥5,000㎡ → tier3 (83件) / ≥2,000㎡ → tier2 (128件) / ≥800㎡ → tier1 (219件)`
   実分布: min 51㎡ / p25 390㎡ / 中央値 798㎡ / p75 1,854㎡ / p90 4,672㎡ / max 152,998㎡

   **区が増えたときに取り直した。** 江東区173件だけだった頃は中央値1,690㎡で
   閾値は 10,000/3,000/1,000 だった。目黒区の児童遊園や杉並区の小さな公園が入って
   分布が下にずれたので、5区まとめて計算し直している。
   江東区の判定も少し動く（5,000㎡の公園が tier2 から tier3 に上がるなど）。
2. **ベンチをハードフィルタから外した** — `minBenchCount` を削除し、
   `preferredSeatingTier` としてスコア加点に降格。下回っても候補から落とさない。

あわせて、同じ「データが無いのに必須条件にしていた」問題を2件修正した:

- `maxTransitWalkM` (最寄バス停) → データが無いためフィルタから削除。`DATA_GAPS` に記録
- `requireStepFree` → `excludeKnownStepped` に変更。
  **「段差ありと明記された場所だけを除外」** する意味に変えた。
  段差データを持たない公園を「非対応」として全滅させないため、
  `place_access.step_free` は三値 (1/0/NULL) にしてある。

| 判定 | 件数 | 備考 |

### T-15 カラムマッピング

`etl/mappings/` に13のマッピング。`role` で place（母集団）と donor（属性の供給元）を分けている。
公衆トイレは**行き先ではなく属性の供給元**なので `role: 'donor'`、places には入らない。

推奨フォーマットの読み方は `_templates.mjs` に一本化してある。
区ごとに写経すると片方だけ直して気付かない事故が起きるため、
区ごとのファイルには**出典と例外だけ**を書く。江東区の公共施設一覧と
目黒区の公園だけは列が独自なので個別に書いてある。

除外の内訳:

| データセット | 読込 | 採用 | 落とし方 |
|---|---|---|---|
| 江東区 公共施設一覧 | 632 | 404 | 大区分・小区分のキーワード |
| 杉並区 公共施設一覧 | 605 | 310 | **名前のキーワードのみ**（区分の列が無い） |

### T-16 正規化・名寄せ・空間結合

| 段階 | 件数 |
|---|---|
| マッピング適用後 | 1,593（公園779 + 施設714） |
| **名寄せ後** | **1,411**（182件を統合） |
| うち空間結合でトイレが付いたもの | 899 |

トイレの空間結合は**区をまたいで許している**。隣の区のトイレが150m先にあるのは
事実であって、行政界で切る理由がない。

名寄せは「江東区立」等の接頭辞を落とした名称キー + 半径100m以内で同一とみなす。
公共施設一覧の小区分「区立公園」173件が都市公園一覧とほぼ完全に重複していたため、
これを行わないと同じ公園が2回出る。

区名の接頭辞は**5区を決め打ちしている**。`[^\s]{1,4}区` のような汎用の書き方だと
「三之輪橋区民広場」の先頭まで削ってしまう。
名寄せのキーには区名も混ぜてある。「中央公園」は杉並にも台東にもあり、別物として残したい。

台東区の公園CSVは**元データ自体に同名の行が複数ある**（山谷堀公園8行、隅田公園4行）。
区間ごとに1行になっている造りで、名寄せで 63 → 50 件になるのは正しい挙動。

**統合時は両方のデータセットを出典として残す。**

### T-19 絞り込み — 間引きは行わなかった

計画では「200件に間引く」としていたが、実データを見て**かけないことにした**。

- bbox フィルタで落ちた件数は **0**。座標の入力ミスは無かった
- 薄い駅ほど間引きの影響を受ける。間引きは**薄い方をさらに薄くする方向にしか働かない**

bbox は区が増えたので**範囲を決めるものではなくなった**。
今は23区の外接矩形で桁ミスを拾い、加えて**区の重心から8km以上離れた点を警告**する。
どちらも現在の1,411件では0件。

清澄白河駅からの到達件数（`config/modes.ts` の MINUTES に対応）:

| 散歩時間 | 距離上限 | 到達件数 |
|---|---|---|
| 30分 | 700m | 26 |
| 60分 | 1,200m | 56 |
| 90分 | 1,700m | 107 |

1,411件は D1 にとって全く負荷にならない規模（DB サイズ 1.5MB）であり、
5区の全域を持っておくと「別の場所を見せて」と自然文検索の母集団が確保できる。
必要になったときのために `node etl/04-select.mjs --limit=200` は残してある。

### D1 の落とし穴: `power()` が使えない

距離計算を SQL 側でやろうとすると引っかかる。

```
power(x, 2) → not authorized to use function: power (SQLITE_ERROR 7500)
```

`sin` / `cos` / `sqrt` / `asin` / `radians` / `abs` は使えるので、
二乗は `x * x` と書けば通る。動作確認済みのクエリを `db/queries.sql` に置いた。
**T-31（距離計算）と T-32（ハードフィルタ）はそれを写して実装すること。**

三値カラムの条件も同じファイルに書いてある。`step_free = 1` ではなく
`(step_free IS NULL OR step_free = 1)` と書かないと、段差データを持たない公園が全滅する。
